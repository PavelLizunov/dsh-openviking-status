# ADR 0004: Release-тарбол как рекомендуемый способ установки

## Статус

Принято (Accepted)

## Контекст

README рекомендовал `dsh plugin add github:dipertq/dsh-openviking-status#vX.Y.Z`.
На практике эта команда у пользователя падала:

```
[ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED] The git-hosted package
"@openviking-community/dsh-openviking-status@0.1.2" needs to execute build
scripts but is not in the "allowBuilds" allowlist.
```

Причина в связке двух фактов:

1. Плагин не хранит `lib/` в git (артефакты сборки в `.gitignore`), поэтому при
   установке из git пакет обязан собраться на машине пользователя — это делает
   скрипт `prepare`.
2. pnpm блокирует сборочные скрипты git-зависимостей, пока пакет не внесён в
   `allowBuilds`. Версия pnpm, встроенная в DSH Desktop (11.8.0), матчит только
   **commit-pinned** ключ вида
   `<name>@https://codeload.github.com/<repo>/tar.gz/<sha>`. Этот ключ меняется
   при каждом пуше, то есть запись нужно добавлять заново для каждой версии.
   Стабильная форма `<name>@git+https://github.com/<repo>.git` появилась только
   в pnpm 11.21 и на 11.8.0 не срабатывает.

Проверено экспериментально в двух чистых проектах без единой записи
`allowBuilds`:

| Способ установки    | Результат                              |
| ------------------- | -------------------------------------- |
| release-тарбол      | успешно, `lib/` на месте               |
| `github:...#v0.1.3` | `ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED` |

Тарбол, собранный `pnpm pack`, уже содержит `lib/`, поэтому `prepare` при его
установке не запускается — а значит и разрешение не требуется.

### Почему ссылка версионная, а не `latest`

Первой редакцией этого ADR рекомендовалась «плавающая» ссылка
`/releases/latest/download/dsh-openviking-status.tgz` — чтобы команда в
документации не устаревала. Проверка показала, что она ломает профиль:

```
[ERR_PNPM_MISSING_TARBALL_INTEGRITY] Cannot install package
"@openviking-community/dsh-openviking-status@https://.../latest/download/dsh-openviking-status.tgz":
its lockfile entry has no "integrity" field
```

Содержимое по такому URL меняется от релиза к релизу, поэтому pnpm не
записывает для него `integrity` — и **любой последующий** `pnpm install` в этом
профиле падает. Первая установка при этом проходит, так что дефект проявляется
не сразу. Версионная ссылка указывает на неизменяемый ассет, получает
`integrity` и переживает повторные установки:

| Ссылка              | Первая установка | Повторный `pnpm install`             |
| ------------------- | ---------------- | ------------------------------------ |
| `latest/download/…` | успешно          | `ERR_PNPM_MISSING_TARBALL_INTEGRITY` |
| `download/vX.Y.Z/…` | успешно          | успешно                              |

## Решение

1. **Рекомендуемый путь в README — release-тарбол с версионной ссылкой.**
   Цена — номер версии в документации нужно обновлять при выпуске; выгода —
   профиль не ломается при переустановке зависимостей.
2. **Путь `github:` описан как запасной** — с явным объяснением, откуда берётся
   `allowBuilds` и почему ключ приходится обновлять. Раньше пользователь
   упирался в ошибку без объяснения.
3. **Публикация в npm добавлена в релизный workflow как опциональный шаг.**
   Секреты не читаются из step-level `if`, поэтому проверка живёт внутри
   скрипта: без `NPM_TOKEN` шаг ничего не делает и релиз остаётся зелёным. Когда
   токен появится, установка упростится до `dsh plugin add <имя пакета>` вообще
   без URL: реестр даёт и `integrity`, и разрешение вопроса `allowBuilds`, то
   есть снимает оба описанных здесь ограничения сразу. Это предпочтительный
   следующий шаг.

## Последствия и компромиссы

- **Плюсы**: установка в одну команду без правки конфигов профиля; повторные
  установки в профиле не ломаются.
- **Минусы**: ссылку в README нужно обновлять при каждом релизе. Автоматизация
  через `latest` отвергнута выше по конкретной причине, а не из-за вкуса.
- **Ограничение**: пока пакет не опубликован в npm, у `github:`-установки
  трение сохраняется — устранить его на стороне плагина невозможно, это
  поведение pnpm 11.8.0.
